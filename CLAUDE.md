## What this app does

EsportManager is a device manager for an esport club, run from a local server machine on the club's LAN. Its purpose:
- **Power on club computers remotely** (Wake-on-LAN) and ping them to track online/offline status.
- **Copy game files to club computers over the network** (via `robocopy`) instead of having each machine download games individually, avoiding slow/duplicated downloads.
- Scan the LAN for devices, list them, and queue/run maintenance operations (copy jobs, wake, etc.) per device with live progress/status feedback.

It is a single-project .NET MAUI Blazor Hybrid desktop/mobile app (project lives in `EsportManager/EsportManager/`, solution file is `EsportManager/EsportManager.slnx`).

## Commands

Build/run from the `EsportManager/` directory (where `EsportManager.slnx` is):

```bash
dotnet build EsportManager.slnx
```

Run on Windows (the actively-used target platform, given `WakeMeOnLan.exe`/`robocopy`/`shutdown` shell-outs are Windows-only):

```bash
dotnet build -t:Run -f net10.0-windows10.0.19041.0 EsportManager\EsportManager.csproj
```

No test project currently exists in the repo. There are no lint scripts beyond standard `dotnet build` warnings.

## Architecture

**Vertical slice, not layered.** Code is organized by feature under `EsportManager/Features/<Feature>/`, each with its own `Models/` subfolder, Razor components, and logic — not by technical layer (no separate global `Services/`/`Repositories/` folders). Sub-features get their own nested folder (e.g. `Features/Devices/UpdateFortnite/`, `Features/Devices/TurnOn/`). Shared layout/routing lives in `Components/` and `Components/Layout/`.

### Device data flow

- Devices are **not** stored in a database. `Features/Devices/Components/DevicesTable.razor` reads a flat CSV file named `devices` from `Environment.CurrentDirectory` (one row per known network device: IP, name, MAC, etc.) into `Device` (`Features/Devices/Models/Device.cs`) objects.
- The `devices` file is regenerated by shelling out to the bundled `WakeMeOnLan.exe` (`/scan` then `/scomma devices`) — see `DevicesTable.ScanForDevices()`. `WakeMeOnLan.exe`/`.cfg` are bundled under `Resources/Raw/` and copied to the output directory (`CopyToOutputDirectory=Always` in the .csproj).
- `LaunchSettings` (`EsportManager/LaunchSettings.cs`, registered as a singleton) reads a `--server <name>` CLI arg (defaulting to `HVKSERVER`) — this is the file-server hostname that game files are copied *from*.
- `Resources/Raw/ShareCDrive.bat` is a helper meant to be run on each *club computer* (not the manager app) to expose its C: drive as `\\<machine>\CDrive`, which is the copy *destination* used by robocopy commands (see `UpdateFortniteButton.razor`).

### Process execution model (`Features/Process/`)

External commands (robocopy, WakeMeOnLan, shutdown) are wrapped via **CliWrap** and modeled as `DeviceProcess` (`Features/Process/Models/DeviceProcess.cs`):
- Wraps a `CliWrap.Command`, streams its events (`Started`/`StandardOutput`/`StandardError`/`Exited`) via `Command.ListenAsync`, and exposes mutable `Status`/`Output`/`Progress` for UI binding.
- `HandleStarted/HandleStandardOutput/HandleStandardError/HandleExited` are `virtual` — subclasses override to specialize parsing/status behavior (inheritance-based specialization is the intended extension point, not composition).
- `RobocopyProcess : DeviceProcess` (`Features/Process/RobocopyProcess/Models/`) overrides these to map robocopy's numeric exit codes to `RobocopyStatus`/`RobocopyErrors` (defined alongside it) and to detect fatal `ERROR <code>` lines in stdout/stderr and cancel the process with a custom `ProcessStatus`.
- `ProcessStatus` (`Features/Process/Models/ProcessStatus.cs`) is a small value-object-style class (static instances like `Initialized`, `Running`, `Finished`, `FinishedWithError`) carrying a MudBlazor `Severity` for UI coloring, backed by localized strings from `AppStrings`.
- `Device.ProcessQueue` (`Features/Devices/Models/Device.cs`) holds a `List<DeviceProcess>` per device; `Device.StartQueue()` runs them sequentially and stops the queue on the first error.
- `ProcessLoggerFactory` (registered as a singleton) creates per-device, per-process-type Serilog file loggers under `<CurrentDirectory>/Logs/<device>_<process>_<date>.txt`; loggers are passed into `DeviceProcess`/`RobocopyProcess` constructors.

### Device power state

`Device.TurnOn`/`Device.CheckStatus` (`Features/Devices/Models/Device.cs`) use `System.Net.NetworkInformation.Ping` (async, with a status callback for UI updates) to poll reachability, setting `Device.Status` (`Offline`/`Online`/`Busy`/`WaitingForResponse`). `Device.TurnOff` shells out to Windows `shutdown /m \\<ip>`. Wake-on-LAN itself goes through `WakeMeOnLan.exe /wakeup <mac>` (currently commented out in `TurnOn`).

### UI

- MudBlazor is used for all UI (`AddMudServices()` in `MauiProgram.cs`); inject services like `ISnackbar` via `@inject`.
- `Components/Routes.razor` → `MainLayout` → `Dashboard.razor` (route `/`) renders `DevicesTable`, whose `RowTemplate` is `DevicesTableRow` and whose expandable child row is `ProcessQueueList` (shows `Device.ProcessQueue`/`CurrentProcess`).
- Per-row action buttons are their own components/sub-features: `CheckDeviceStatusButton`, `ShowDetailsButton`, `TurnOnDeviceButton`, `UpdateFortniteButton` — each takes a `[Parameter] Device? Device` and triggers the corresponding `Device`/`DeviceProcess` operation.
- All user-facing strings go through `EsportManager.Resources.Strings.AppStrings` (RESX-generated) — do not hardcode UI strings.

## Conventions (from `.github/copilot-instructions.md`)

- **.NET 10 / C# 14**, `Nullable` and `ImplicitUsings` enabled.
- File-scoped namespaces; `_camelCase` private fields, `PascalCase` public properties.
- Nest tightly-coupled enums inside their owning class (e.g. `Device.StatusEnum`).
- Prefer collection expressions (`[]`) over `new List<T>()`.
- Use `CliWrap` for external process execution; use inheritance/`virtual` methods to specialize process behavior (pattern established by `RobocopyProcess : DeviceProcess`).
- Don't add comments unless matching existing style or explaining genuinely complex logic.
- Prefer existing libraries (CliWrap, MudBlazor, Serilog) over adding new packages.
